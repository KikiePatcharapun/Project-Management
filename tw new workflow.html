TW Development Workflow (updated Q2 '26)

📋 Mellowmatic 📊 Gitea Board 💬 Discord
🔄 Daily Status Meeting: Teams ensure Mellowmatic + Gitea are up-to-date before meeting

Key Daily Actions by Role

📋 PO

Mellowmatic
  • • Create main task with requirements
  • • Define scope and acceptance criteria
  • • Breakdown required teams on task description
Discord
  • • Create new Discord post/thread: "New Feature: [Name]" with @PM
  • Signtrust & Genesis (Throughwave server) > Current forum channel: new post for new spec
  • Fourgle (Fourgle Workspace server) > New text channel, new thread for new spec
  • - On Spec-working phase, give action plan and list required resources (reviewers/blockers)
  • • Inform if briefing is needed or sufficient task details are given
  • • Support development flow/gap when required
Gitea
  • • Managing Spec to Spec done states
  • • Support development flow/gap when required

📊 PM

Discord

Read PO's Discord post with feature requirements

Mellowmatic
  • • Create tasks for required team as PO identified
  • • Monitor if details are up-to-date based on discord communication
Discord
  • • Tag @team-members in PO's thread with their assigned tasks
  • • Make sure everyone understand what to do
  • • Mellowmatic cards pinned in each post/thread
  • • Check daily: Blockers? Delays? Need help?
Gitea Board
  • • Create "[Feature] - Main Task" with progress checklist
  • • For ad-hoc support task, update when notified
  • • Maintain correct card status

💻 Dev/Design

Discord
  • • Check #pmo-dev, #pmo-design for team/product priority
  • • Check mentioned (assigned tasks) and raise up if scope/action plan is unclear
Mellowmatic
  • • Read Mellowmatic task details and estimate
  • • Make sure your card remains true as a source of truth
Discord
  • • Use thread to update progress, ask questions or separate #dev-room for internal team discussions
  • Signtrust & Genesis (Throughwave server) > Current forum channel: new post for new spec, existing separated dev room (post)
  • Fourgle (Fourgle Workspace server) > New thread for new spec (one new text channel), existing separated dev channel
  • • Raise concerns/blockers
  • • Inform in the thread when there's a delay or re-estimation + update in Mellowmatic
Gitea
  • • Recheck or correct status before/during status meeting
  • • Raise blockers affecting your tasks

Gitea Columns Usage

Remark: To reflect real-time transition, card must be updated by task owner as some changes/decisions might be made unnoticed by PM and cards are not updated by the time status meeting starts. Task owner makes correction during this time.

📋 Backlog

  • • List of product backlog
  • • PM creates when confirmed with PO
Remark: For general team's tasks, inform PM to create via #pmo-dev, #pmo-design, QSquad channel, or create own task and notify @PM.

📝 Spec

  • • PO moves card from Backlog to Spec when starts working on Spec
  • • PO creates Spec subtask and add reviewers as shared Owners
  • • PO moves to Spec done when finalized

✅ Spec Done

  • • PM creates to-do list on description for required team as stated in Mellowmatic (Design, BE, FE, + QA Prep) and assign team lead or designated owner
  • • Team lead reassign to team members if required
  • • PM check Mellowmatic and reflects estimated plan/subtasks on the card
  • • PM or Team that is ready to start moves card to Working state

⚙️ Working

  • • When task is done, task owner is unassigned and reassign the next person based on checklists
  • • If rejected, reviewer reassigns back to task owner
  • • If approved, reviewer assign mergers or release engineers
  • • Release engineers or PM moves card to On Hold/Waiting until QA is ready to start
Remark: Dev teams only update on their part regardless of other teams' status sharing the same card.

⏸️ On Hold/Waiting

  • • Reasons and planned dates must be clearly stated on the card (assignee's time conflict to other tasks, dependencies, etc.)
  • • PM notify task blockers' responsible person and actively update progress

🧪 QA Testing

  • • QA moves card from On Hold/Waiting state when QA is ready to start testing
  • • QA add new checklists for testing with estimation
  • • If Rejected, QA moves card to Fix bugs and reassign to Dev in charge or PM
  • • If Passed, QA reassigns main card back to Release engineers
Remark: QA Prep task includes all preparation stage; test case, test plan, etc., this can start at the Spec done state

🐛 Fix Bugs

  • • Dev add checklist for support/Fix bugs
  • • Use the same review process as in Working state
  • • Release engineers/PM reassigns QA and moves to On Hold/Waiting until QA is ready to start

🎉 Done

  • • PO/PM/Release engineers confirm and move task to Done
